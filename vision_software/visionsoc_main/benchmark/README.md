# benchmark_instructions_perf — FPGA instruction benchmark

FPGA (KV260) port of the t1emu test
`tests/vision_task/benchmark_instructions_lmul1.c`. It runs the same 35
instruction micro-kernels (29 compute + 6 LSU) in both Horizontal and Vertical
CSR-0x7c0 modes on the real T1 in the PL, and measures **per-instruction
hardware cycles** with the libt1 perf counter.

Unlike the t1emu test it takes **no camera frame** — operands are dummy data
written straight into the **URAM scratchpad**, and every `vle`/`vse`/`vlse`/`vsse`
loads/stores from the scratchpad (rs1 = `T1_SCRATCHPAD_PA` region), as requested.

```
benchmark/
├── benchmark_instructions_perf.c   the main (mirrors matmul_8bitraw_short_perf.c)
├── Makefile                        builds the kernel header + the binary
├── run_bench.sh                    one-shot: build + run + plot
├── plot_bench_cycles_fpga.py       landscape, big-font chart (reads bench.csv)
├── README.md
└── kernels/
    ├── bench_instructions.S        the 39 bare vector ops (6 setup + 33 timed)
    └── bench_instructions.h        generated by build_kernel.sh (on the board)
```

## How it works

- `kernels/bench_instructions.S` is just the raw vector ops (no `vsetvli`/`csrw`
  — `vtype`/`vl`/`vertical_mode` are host-side fields of `struct t1_op`).
  `build_kernel.sh` assembles it to `bench_instructions[]` (one `uint32_t` word
  per op). The harness's `BI_*` enum indexes that array **positionally**, so the
  op order in the `.S` and the enum must stay in lockstep.
- The harness allocates 3 scratchpad buffers (A/B operands, C store target),
  writes dummy data, then per mode: issues a 6-op **setup** (load A→v8, B→v12,
  zero v16/v20, build masks v0/v1) once, then **times** each of the 35 tests by
  issuing the op `--iters` times, each bracketed by
  `t1_perf_start`/`t1_issue`/`t1_wait_ready`/`t1_perf_stop`, summing cycles.
- It prints `[PERF] counter <tag> START/STOP` lines with the **same tag layout**
  as `plot_bench_cycles.py` (H = 1..35, V = 36..70), so both plot scripts parse
  it. The STOP cycle is the **sum over `--iters` issues**; divide by `--iters`
  for cycles/issue.

> Note: on hardware the measured cycles include the AXI-Lite issue +
> writeback-drain handshake per op, so they are **not** directly comparable to
> the tight t1emu replay loop — they are the real per-issue FPGA cost.

## Build + run + plot — one command

```sh
cd vision_software/visionsoc_main/benchmark
./run_bench.sh 100          # 100 issues averaged per (instruction, mode)
```

`run_bench.sh` **auto-detects where it is** and does everything in one shot:

- **From the dev host** (no `/dev/uio0`): syncs the sources to the Kria over
  `ssh kv260`, builds + runs there in `--local` mode, scp's the CSV back, and
  renders the chart locally (the dev host has matplotlib). Override the target
  with `--host <name>`. This is the normal case — the dev host has neither the
  rv32 assembler nor the T1 hardware, so the build+run must happen on the board.
- **On the board** (`/dev/uio0` present): `make` (builds
  `kernels/bench_instructions.h` via `build_kernel.sh`, then the binary), stops
  `visionsoc_main` to free T1, runs the benchmark as root, restarts
  `visionsoc_main`, and plots. It does **not** touch the camera/display.

Force a mode with `--local` / `--remote`; skip the chart with `--no-plot`.
Results land in `results/<ts>/`:

```
results/<ts>/bench.log              full stdout
results/<ts>/bench.csv              tag,mode,instruction,iters,total_cycles,cyc_per_iter
results/<ts>/bench_cycles_fpga.png  the landscape chart
```

If the board has no `matplotlib`, step 5 is skipped with the exact command to
run on a host that does. Pull `bench.csv` and render there:

```sh
./plot_bench_cycles_fpga.py results/<ts>/bench.csv
# knobs: --scale 1.8 (even bigger), --annotate (values on bars), --out chart.png
```

### Pieces individually

```sh
make                                                    # build only
sudo ./benchmark_instructions_perf --iters 100 --out /tmp/bench.csv | tee /tmp/bench.log
./plot_bench_cycles_fpga.py /tmp/bench.csv              # landscape, big font
../../../plot_bench_cycles.py --log /tmp/bench.log --iters 100   # original chart (parses [PERF])
```

The new plot reads `bench.csv` (the canonical FPGA artifact, same shape as
`run_perf.sh`'s `/tmp/*_perf.csv`); it also accepts a captured stdout log as a
fallback (auto-detected). The original `plot_bench_cycles.py` parses the
`[PERF] counter START/STOP` lines the harness also prints to stdout.
